# 决策记录

## D001：首个领域

首个领域固定为 Computer Vision，通过通用 Field 和领域配置包保留扩展入口。

## D002：编排方式

优先验证当前会话中的强力模型主编排与执行子代理协作，不先建设独立 Harness 应用。项目文件是跨模型和跨会话的事实状态。

## D003：首次实验范围

首次闭环只实现基础数据与校验，不引入实时网页数据、前端、数据库或第三方依赖，以隔离模型协作质量。

## D004：验收方式

执行模型的自述不构成完成依据；强力模型必须检查实际文件并独立运行验证命令。

## D005：首次子代理路由

TASK-001 中，编排接口接受 HY4 Flash 模型选择并成功完成子代理执行。后续继续采用当前会话主编排；每次仍须独立验收，不能以路由成功代替结果验证。

## D006：长任务监督

主代理以里程碑而非单个子任务为结束单位，通过 SUPERVISION.md 和 STATE.json 持续派发、等待、验收与 checkpoint。活跃会话中不因中间成果停止；进程或会话中断后按文件恢复，不作离线常驻承诺。

## D007：M3 技术栈与数据边界

M3 使用 React、TypeScript、Vite 和 Vitest，直接读取现有领域包，投稿计划仅存浏览器 localStorage。首版不引入后端；投稿计划使用用户明确输入的目标日期，不将虚构样例或未经核验的实时信息展示为正式数据。

## D008：开源自托管交付

产品为开源、本地自托管的工具，用户从 GitHub 仓库下载并用自己的 API Key 运行，不面向公网部署。仓库需具备 README、LICENSE、示例配置和免责声明；所有凭据本地保存，仓库不内置密钥。

## D009：模型角色调整

强力/规划模型由 Kimi K3.1 Pro 切换为 DeepSeek-V4-Pro（当前会话）。执行模型继续使用 HY4-FLASH，受约束完成小范围任务。任务契约、验收与监督机制保持不变。

## D010：HY4-FLASH 后台执行不可靠

TASK-003 两次派发 HY4-FLASH 后台子代理，均长时间无产出并卡住（一次约 12 分钟、一次约 1 分钟无文件）。诊断判定该环境后台 HY4-FLASH 对多文件编码任务不可靠。策略：核心代码改由规划模型直接编写并确定性验证；HY4-FLASH 仅用于范围更小、更单一的任务，并缩短观察窗口。

## D011：HY4-FLASH 卡住根因诊断（2026-11-20）

三组最小后台探针全部成功：仅写文件、运行简单命令、运行 `npm run build` 长命令，均秒级完成并正确返回。结论：后台执行机制与 HY4-FLASH 路由本身正常，卡住与「运行命令」无关。真正的差异变量是 TASK-003 的任务规模（需同时编写十余个文件、安装依赖并自验），属于**任务粒度过大导致执行模型在长时间多步工具调用中停滞**，而非环境故障。后续对策：把多文件编码任务进一步拆小、或由规划模型直接实现；HY4-FLASH 只承担单文件或单命令级小任务，并设短观察窗口，超时即由规划模型接手。
